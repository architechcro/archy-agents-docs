    Flows¶

    Provision a tenant and bootstrap an admin¶

    sequenceDiagram
    autonumber
    participant B as Your backend
    participant A as Archy API
    participant U as Admin user
    B->>A: PUT /integrations/provisioning/orgs/{org_id} (service token)
    A-->>B: org_id, created
    B->>A: PUT .../orgs/{org_id}/projects/{project_id}
    A-->>B: project_id, created
    B->>A: POST .../orgs/{org_id}/admins/invite {email}
    A-->>B: invite_link (single use), user_id
    B->>U: Send the set-password link
    U->>A: POST /auth/reset-password {token, new_password}
    A-->>U: ok
    U->>A: POST /auth/login
    A-->>U: user token (org_id, project_id)

    Ingest and index documents¶

    sequenceDiagram
    autonumber
    participant C as Client
    participant A as API
    participant S as Object storage
    participant Q as Indexing job queue
    participant W as Indexer
    participant E as Embedding model
    participant V as Qdrant
    C->>A: POST .../knowledge-bases/{kb}/documents/upload (multipart)
    A->>S: store original file
    A->>Q: enqueue one job per document
    A-->>C: documents with status "uploaded"
    W->>Q: take job (running)
    W->>S: read file
    W->>W: extract text and chunk
    W->>E: embed chunks (organization credential)
    W->>V: upsert vectors
    W->>Q: succeeded (document status "indexed")
    C->>A: GET .../knowledge-bases/{kb}/stats
    A-->>C: files_total, indexed_total, indexing_total

    An indexing job moves through the states below. A failed job keeps error_type and error_message; re-run it with POST .../index.

    stateDiagram-v2
    [*] --> queued
    queued --> running
    running --> succeeded
    running --> failed
    failed --> queued: re-enqueue
    succeeded --> [*]

    Ask an agent¶

    sequenceDiagram
    autonumber
    participant C as Client
    participant A as API
    participant R as Model resolver
    participant K as Knowledge base
    participant L as LLM provider
    participant T as MCP tools
    C->>A: POST /agents/{id}/query {message, session_id?}
    A->>A: authenticate, check tenant
    A->>R: resolve provider, model, credential
    R-->>A: verified credential or credential error
    A->>K: retrieve top_k chunks (if the agent has a knowledge base)
    loop until final answer or max iterations
        A->>L: messages, tools, context
        L-->>A: text or tool call
        opt tool call
            A->>T: call tool
            T-->>A: result
        end
    end
    A->>A: persist session, record token usage
    A-->>C: output, session_id

    Run a workflow asynchronously¶

    sequenceDiagram
    autonumber
    participant C as Client
    participant A as API
    participant W as Workflow engine
    C->>A: POST .../workflows/{id}/runs {message, inputs}
    A-->>C: 202 run_id, status pending
    A->>W: start in background
    loop poll
        C->>A: GET .../runs/{run_id}
        A-->>C: status running
    end
    W-->>A: finished
    C->>A: GET .../runs/{run_id}
    A-->>C: status succeeded, output, audit
    stateDiagram-v2
    [*] --> pending
    pending --> running
    running --> awaiting_input: checkpoint node
    awaiting_input --> running: resume with answer
    awaiting_input --> cancelled: cancel
    running --> succeeded
    running --> failed
    succeeded --> [*]
    failed --> [*]
    cancelled --> [*]

    Pause for a human and resume¶

    sequenceDiagram
    autonumber
    participant C as Client
    participant A as API
    participant H as Human
    C->>A: POST .../workflows/{id}/execute
    A-->>C: status awaiting_input, pending_input, session_id
    C->>H: show the question
    H-->>C: answer
    C->>A: POST .../workflows/{id}/sessions/{session_id}/resume {answer}
    A-->>C: continues, status completed

    Connect an AI client to the MCP server¶

    sequenceDiagram
    autonumber
    participant C as MCP client
    participant M as MCP server
    participant A as Archy API
    participant U as User (browser)
    C->>M: request without token
    M-->>C: 401 with resource_metadata
    C->>M: GET /.well-known/oauth-protected-resource/mcp
    M-->>C: authorization server = Archy API
    C->>A: GET /.well-known/oauth-authorization-server
    C->>A: POST /oauth/register (dynamic client registration)
    C->>U: open /oauth/authorize (PKCE S256)
    U->>A: sign in and approve
    A-->>C: authorization code on redirect URI
    C->>A: POST /oauth/token (code, code_verifier)
    A-->>C: access token
    C->>M: tools/call with Authorization: Bearer
    M->>A: same call with the caller token
    A-->>M: result scoped to the caller's tenant
    M-->>C: tool result

    Clients that cannot run OAuth use an archy_mcp_ API key instead. See Connect a client.

    Which model runs¶

    flowchart TD
    S([Execution starts]) --> A{Attachment on the agent?}
    A -- yes --> USE[Use that credential and model]
    A -- no --> B{Agent config pins credential_id and model_name?}
    B -- yes --> USE
    B -- no --> C{Project attachment?}
    C -- yes --> USE
    C -- no --> C2{Project platform default model?}
    C2 -- yes --> PLAT[Platform model, no credential]
    C2 -- no --> D{Organization attachment?}
    D -- yes --> USE
    D -- no --> D2{Organization platform default model?}
    D2 -- yes --> PLAT
    D2 -- no --> E{Agent config has a model_name?}
    E -- yes --> PLAT
    E -- no --> ERR[No model: error or echo mode]

    A tier is skipped when its credential is missing or not verified. The platform tiers run only when the organization allows the platform fallback. When none applies the call fails with a credential_error rather than silently using a platform key.
