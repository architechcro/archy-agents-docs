    For AI agents¶

    These docs are written to be read by people and by AI agents (coding assistants, autonomous agents, retrieval systems). This page explains how to consume them efficiently and lists the facts and traps an agent most needs.

    Machine-readable entry points¶

    Resource URL (relative to the site root) Use
    llms.txt /llms.txt Index of the documentation in the llms.txt format
    llms-full.txt /llms-full.txt Full text of the guides, tutorials and MCP pages in one Markdown file. Load it as context.
    openapi.json /openapi.json OpenAPI 3.1 specification of every public endpoint and schema
    API reference pages /reference/<group>/ Per-endpoint parameters, examples and responses
    MCP resources archy://workflows/authoring-guide and three more Live workflow contracts served by the MCP server

    A running API also serves its own live copy of the specification at /openapi.json.

    Recommended reading order for an agent

    1. llms.txt to pick pages.
    2. This page for the rules and traps below.
    3. The guide that matches the task (provisioning, knowledge bases, agents, workflows).
    4. openapi.json (or the reference page) for exact request and response shapes.

    Ground rules¶

    1. Never print, log or store secrets. Bearer tokens, archy_mcp_ keys, provider API keys and invite_link values are secrets. Read them from the environment.
    2. Check your credential type before you call. User tokens for tenant routes, service tokens for /integrations/provisioning, archy_mcp_ keys only for the MCP server and its tool routes.
    3. Use ids, not names. Every resource has a UUID. Names are not unique keys.
    4. Prefer idempotent calls and verify the result with a read call after every write.
    5. Ask before destructive actions (DELETE, replacing an agent config, deleting a knowledge base or a credential).
    6. Treat model output as untrusted. Validate structured output before acting on it.
    7. Use async runs for long work and poll; do not hold a connection for minutes.

    Task playbooks¶

    Bootstrap a tenant (service token)¶

    1. PUT /api/v1/integrations/provisioning/orgs/{org_id} with {"name": ...}.
    2. PUT /api/v1/integrations/provisioning/orgs/{org_id}/projects/{project_id}.
    3. POST /api/v1/integrations/provisioning/orgs/{org_id}/admins/invite with {"email": ...}; take the token from invite_link.
    4. POST /api/v1/auth/reset-password with {"token", "new_password"}; then POST /api/v1/auth/login.
    5. Verify with GET /api/v1/tenancy/whoami.

    Connect a model (admin user token)¶

    1. POST /api/v1/llm-providers/credentials with provider, display_name, api_key (and base_url where needed).
    2. POST /api/v1/llm-providers/credentials/{id}/verify; continue only if success is true.
    3. PUT /api/v1/llm-providers/model-attachments/org with credential_id and model_name.
    4. PUT /api/v1/llm-providers/embedding-default before creating knowledge bases.

    Knowledge base to answer¶

    1. POST .../knowledge-bases, then POST .../knowledge-bases/{kb}/documents/upload (multipart files).
    2. Poll GET .../knowledge-bases/{kb}/stats until indexing_total is 0 and indexed_total equals files_total.
    3. POST .../knowledge-bases/{kb}/query to check retrieval.
    4. POST .../agents with config.knowledge_base_id; POST /api/v1/agents/{agent}/query.

    Workflow from a graph¶

    1. Read GET /api/v1/workflow-authoring-guide and GET /api/v1/workflow-node-types.
    2. Create or reuse a workflow, then POST .../workflows/{id}/validate with the draft graph until valid is true.
    3. Save with PUT, validate the saved workflow, then run with POST .../workflows/{id}/runs and poll.

    Facts that are easy to get wrong¶

    Topic Fact
    Base path Everything is under /api/v1. Tenant routes are /api/v1/orgs/{org_id}/projects/{project_id}/... and the ids must match the token.
    Roles A self-registered user has role permission-admin and cannot create LLM credentials (403 Org admin role required). admin membership comes from provisioning or the invite flow.
    Verified credentials Only verified credentials run. Attaching an unverified credential returns 422.
    Model choice Org and project defaults come from model attachments, not from is_default. An agent config.model without credential_id runs on the platform model, not on the customer's key.
    Embeddings Set the organization embedding default before creating knowledge bases. Do not change the embedding model of a populated knowledge base.
    Agent update PUT replaces the whole config. Read, modify, write the complete object.
    Agent config Unknown keys are rejected with 400.
    Echo mode If no model resolves, an agent may reply Echo: <your message> with meta.mode = "echo". That is a configuration problem, not an answer.
    Workflow save Saving a composite workflow enforces node-name rules only. Call validate; do not rely on save to reject a bad graph.
    Expressions A template may read only nodes that run before it (TEMPLATE_NODE_NOT_UPSTREAM). A checkpoint's answer is nodes.<checkpoint name>.output.
    Sensitive inputs Masked in traces and must be resent when a paused run resumes.
    Streams Failures arrive in-band (event: error) after a 200. Use fetch/httpx.stream, not EventSource.
    Async runs POST .../runs returns 202 and a run_id; poll GET .../runs/{run_id} for succeeded, failed or awaiting_input.
    Service tokens They may call tenant routes for the org and project in the path, but have no org-admin rights. They cannot create credentials through /llm-providers or set model attachments.
    Provisioning PUT upserts with ids you choose. 409 bodies carry detail.code.
    Secrets API keys and MCP headers are write-only and are never returned.

    Using Archy through MCP¶

    If you are an agent with MCP support, connect to the Archy MCP server instead of calling REST: see Connect a client. Start with auth_whoami, read the archy://workflows/* resources before you author a workflow, and use workflow_validate before saving. The Tool catalog lists every tool and its arguments.

    Citing and linking¶

    Every endpoint has a stable anchor of the form #op-<method>-<path> on its reference page (for example reference/agents/#op-post-api-v1-agents-agent-id-query). Guides link to the reference sections they use. Prefer linking to these anchors when you report which call you made.
