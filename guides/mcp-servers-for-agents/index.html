    External MCP servers and skills¶

    Agents become more useful when they can act: search Jira, query a database, call your internal API. The Model Context Protocol (MCP) is the standard way to expose such tools. In Archy you register an MCP server once and attach it to the agents that may use it.

    Two different MCP topics

    This page is about MCP servers that agents call (tools for your agents). To let an AI client call Archy (Claude, Copilot, Cursor, ...), see MCP.

    flowchart LR
    REG[Registered MCP server] -->|attach| AG[Agent]
    AG -->|tool call| REG
    REG --> EXT[Your tool service]
    HC[Health scheduler] -->|checks| REG
    AG --> LOG[Tool invocation log]

    All paths below start with /api/v1/orgs/{org_id}/projects/{project_id}.

    BASE="$ARCHY_API_URL/api/v1/orgs/$ORG_ID/projects/$PROJECT_ID"

    Register a server¶

    curl -s -X POST "$BASE/mcp-servers" \
  -H "Authorization: Bearer $ARCHY_TOKEN" -H "Content-Type: application/json" \
  -d '{
    "name": "tickets",
    "transport": "http",
    "config": {
      "base_url": "https://mcp.example.com",
      "headers": {"Authorization": "Bearer <service key for that server>"}
    }
  }'
    Field Meaning
    name Human readable name (not enforced unique). required_mcp_servers entries match a server by id or by name, ignoring case and punctuation.
    transport http (or streamable-http) for a remote server. stdio servers are created from an organization template (see below); transport is ignored for template instances.
    config For http: base_url, optional path (default /mcp), headers and stateful. env values apply only to stdio template instances; for template instances config is validated against the template's schema (422 on mismatch).
    template_id, instance_label Create an instance of an organization template

    Secrets are write-only. All headers and env values, keys with credential-like names (token, api_key, password, secret), template fields marked x-sensitive and credentials inside URLs are encrypted at rest and returned as ***REDACTED*** by every endpoint. To keep a secret, send the placeholder back unchanged. To change it, send the new value. If an update adds a new URL origin, or changes a non-secret entry in the same headers or env block, re-enter the secrets too. Values that start with enc:v1: are rejected (422), and saving a secret fails with 503 when the deployment has no encryption key.

    Remote server URLs are validated against SSRF rules. URLs must use https://; plain http://, private and loopback addresses need an operator setting (SSRF_ALLOW_LOCAL_URLS, SSRF_ALLOW_PRIVATE_NETWORKS or SSRF_ALLOWED_INTERNAL_HOSTS), and cloud metadata hosts are always blocked.

    Attach to an agent¶

    curl -s -X POST "$BASE/agents/$AGENT_ID/mcp-servers/$SERVER_ID/attach" -H "Authorization: Bearer $ARCHY_TOKEN"
curl -s "$BASE/agents/$AGENT_ID/mcp-servers" -H "Authorization: Bearer $ARCHY_TOKEN"
curl -s -X POST "$BASE/agents/$AGENT_ID/mcp-servers/$SERVER_ID/detach" -H "Authorization: Bearer $ARCHY_TOKEN"

    In a composite workflow you can attach a server to one node with a satellite-mcp resource node instead. See Attach resources.

    Control which tools run¶

    Where How
    Per workflow node toolAllowlist on the satellite-mcp node (omit to allow all)
    Per run mcp_enabled: false turns MCP off; mcp_tool_allowlist: ["jira_get_issue"] registers only those tools (server side names, without the server prefix)
    Required servers required_mcp_servers on a sequential or composite workflow fails the run with MCP_UNAVAILABLE when a server is down, instead of silently skipping it

    Pass the per-run options in the body of /execute, /execute/stream or /runs. They are not stored.

    Health and observability¶

    Need Request
    Latest health of a server GET .../mcp-servers/{server_id}/health/latest
    History GET .../mcp-servers/{server_id}/health
    Check now (platform admins only; at most once per 30 seconds per server, otherwise 429) POST .../mcp-servers/{server_id}/health/check
    Status of an agent's servers GET .../agents/{agent_id}/mcp-status
    Tool invocation log GET .../mcp/tool-invocations
    One invocation GET .../mcp/tool-invocations/{invocation_id}
    Metrics of invocations GET .../mcp/tool-invocations/metrics
    Re-run an invocation (at most 10 per minute per project) POST .../mcp/tool-invocations/{invocation_id}/replay

    A background scheduler checks each project's servers every 60 seconds by default (GET {base_url}/health for HTTP servers) and backs off up to 300 seconds after failures. The interval cannot be changed through the API; operators can turn the scheduler off with HEALTH_SCHEDULER_ENABLED=false.

    Organization templates¶

    Platform administrators publish templates that describe how to reach or launch a server and which config fields are sensitive. Projects then create instances from a template with their own values. Templates are the only way to run stdio servers: creating a stdio server without a template returns 403, and the command always comes from the template and must be an approved command (default npx, uvx, uv, node, python, python3). An instance can only set the env keys its template declares.

    # List the templates of the organization
curl -s "$ARCHY_API_URL/api/v1/orgs/$ORG_ID/mcp-templates" -H "Authorization: Bearer $ARCHY_TOKEN"

# Create an instance from a template
curl -s -X POST "$BASE/mcp-servers" \
  -H "Authorization: Bearer $ARCHY_TOKEN" -H "Content-Type: application/json" \
  -d "{\"name\": \"jira-prod\", \"transport\": \"stdio\", \"template_id\": \"$TEMPLATE_ID\", \"instance_label\": \"production\", \"config\": {}}"

    Skills¶

    A skill is an instruction set (a SKILL.md document) that is appended to the system prompt on every run of an agent it is enabled or attached on. There are two kinds.

    • Skills on disk: shipped with the deployment. GET /api/v1/skills lists them, GET /api/v1/skills/{skill_id} shows metadata and GET /api/v1/skills/{skill_id}/content returns the SKILL.md. Enable them on an agent with config.skills_enabled.
    • Skills in the database: created through the API and scoped to a project.
    # Create a skill
curl -s -X POST "$BASE/skills" \
  -H "Authorization: Bearer $ARCHY_TOKEN" -H "Content-Type: application/json" \
  -d '{"name": "refund-policy", "description": "How to handle refund requests", "skill_content": "# Refund policy\n\nRefunds are allowed within 30 days..."}'

# Attach it to an agent
curl -s -X POST "$BASE/agents/$AGENT_ID/skills" \
  -H "Authorization: Bearer $ARCHY_TOKEN" -H "Content-Type: application/json" \
  -d "{\"skill_id\": \"$SKILL_ID\"}"

# List, detach
curl -s "$BASE/agents/$AGENT_ID/skills" -H "Authorization: Bearer $ARCHY_TOKEN"
curl -s -X DELETE "$BASE/agents/$AGENT_ID/skills/$SKILL_ID" -H "Authorization: Bearer $ARCHY_TOKEN"

    Atlassian access for agents¶

    An agent can use Jira and Confluence on behalf of a person. The person creates a personal Atlassian connection (POST /api/v1/orgs/{org_id}/integrations/atlassian), then grants it to an agent (PUT .../agents/{agent_id}/integration-grants). The credentials never leave the platform and the agent acts only while that person initiates the run. See the Connections and integrations reference.
