    Workflows¶

    A workflow coordinates several agents (and sometimes tools and other workflows) to complete a task that one agent cannot do alone. Archy supports two families:

    • Legacy typed workflows (this page): choose a pattern such as sequential or debate and list the agents. Quick to set up.
    • Composite workflows (next page): a graph of nodes and edges with inputs, variables, conditions, loops, human checkpoints and file output. Use it when you need control.

    Workflows live in /api/v1/orgs/{org_id}/projects/{project_id}/workflows (or /api/v1/orgs/{org_id}/workflows for organization scope). Every PUT that leaves the workflow with a config stores a snapshot as a new version you can list and read (creating a workflow does not). Organization-scope workflows support only create, list, get and execute; everything else on this page is project-scoped.

    Create a workflow¶

    BASE="$ARCHY_API_URL/api/v1/orgs/$ORG_ID/projects/$PROJECT_ID"

curl -s -X POST "$BASE/workflows" \
  -H "Authorization: Bearer $ARCHY_TOKEN" -H "Content-Type: application/json" \
  -d "{
    \"name\": \"draft-and-edit\",
    \"description\": \"A writer drafts, an editor improves\",
    \"type\": \"sequential\",
    \"config\": {\"agent_ids\": [\"$WRITER_ID\", \"$EDITOR_ID\"]}
  }"

    {
  "id": "313bacab-956b-4366-8f82-f134407f0d61",
  "org_id": "84eab6dd-2cc1-41d9-a5e7-0c5e38197865",
  "project_id": "f834cf48-7bf7-4489-8b4b-9c7d8c832cb5",
  "scope": "project",
  "name": "draft-and-edit",
  "description": "A writer drafts, an editor improves",
  "type": "sequential",
  "config": {"agent_ids": ["26fc2a0e-...", "dd7b220d-..."]},
  "legacy_history": false,
  "executable": true
}

    The config is validated against the type. A violation returns 422:

    {"detail": [{"type": "value_error", "loc": ["body"], "msg": "Value error, config.agent_ids is required"}]}

    Workflow types¶

    type Pattern Required config
    sequential Agents run one after another; each receives the previous output agent_ids (list)
    parallel All agents work on the same input at once; outputs are combined agent_ids
    dialog Agents take turns in a conversation agent_ids, optional turns (1 to 100)
    conversation Multi-agent conversation over a shared message hub agent_ids (at least 2), optional turns (1 to 200)
    routing A router agent, keyword routes or a default agent decide who handles the request (see below) default_agent_id; optional router_agent_id, routes, route_map, routing_tool_names
    orchestrator A manager delegates to workers, or a RAG orchestrator compares two knowledge bases manager_agent_id and worker_agent_ids, or kb_a_id and kb_b_id (optional top_k 1 to 50)
    business-pipeline Business agents first, then pipeline agents business_agent_ids, pipeline_agent_ids, optional business_mode (parallel or sequential)
    staged Ordered stages, each parallel or sequential, optionally fanned in stages (list of {agent_ids, mode, name}), optional fanin
    handoff Workers (agents, tools or sub-workflows) are selected by keyword matches workers (at least 2) with kind agent, tool or sub_workflow; optional max_workers
    debate Solver agents argue for several rounds and a moderator decides solver_agent_ids (at least 2), moderator_agent_id, optional rounds (1 to 20)
    interactive-orchestrator Multi-turn orchestration with one manager manager_agent_id; optional knowledge_base_id, structured_output_schema
    composite A graph definition See Composite workflow graphs
    two-agent Legacy; only used by the two-agent SSE endpoint none

    A workflow with no type is treated as sequential.

    Read-only legacy rows

    Old history rows of types intake_generation, backlog_refine, backlog_enhance and backlog_split can still be listed. They show executable: false and legacy_history: true, and new ones can no longer be created.

    Sequential step input¶

    By default a sequential step only sees the previous step's output. To also give every step the original assignment, set:

    {
  "agent_ids": ["...", "..."],
  "step_input_mode": "assignment_plus_previous",
  "handoff_instructions": "Keep the tone formal."
}

    step_input_mode is previous_output (default) or assignment_plus_previous. handoff_instructions is text of at most 8000 characters that is appended to each step's input when step_input_mode is assignment_plus_previous (it is ignored otherwise).

    Require MCP servers¶

    For sequential and composite workflows you can fail fast when a tool server is down:

    {"agent_ids": ["..."], "required_mcp_servers": ["jira", "confluence"]}

    When a listed server is not connected the node fails with MCP_UNAVAILABLE and the run fails.

    How routing and handoff decide¶

    Routing decides in this order: (1) the router agent (router_agent_id) replies with JSON {"route": "<key>"}, a key of route_map, or {"agent_id": "<uuid>"} (a tool call also works when routing_tool_names is set); (2) otherwise routes entries {contains, agent_id} are matched case-insensitively against the message; (3) otherwise default_agent_id handles it. Without a router_agent_id there is no model-based routing.

    Handoff first picks the workers whose matches keywords appear in the message (case-insensitive), then fills up to max_workers (default 2) with the remaining workers in configuration order. Every selected worker runs. kind defaults to agent; kind: tool supports only the built-in test tools echo, uppercase and fail.

    Examples¶

    {
  "name": "triage",
  "type": "routing",
  "config": {
    "router_agent_id": "<router agent>",
    "default_agent_id": "<general agent>",
    "route_map": {"billing": "<billing agent>", "technical": "<tech agent>"}
  }
}

    {
  "name": "decision",
  "type": "debate",
  "config": {
    "solver_agent_ids": ["<optimist>", "<skeptic>"],
    "moderator_agent_id": "<moderator>",
    "rounds": 3
  }
}

    {
  "name": "report",
  "type": "staged",
  "config": {
    "stages": [
      {"name": "collect", "mode": "parallel", "agent_ids": ["<a>", "<b>"]},
      {"name": "write", "mode": "sequential", "agent_ids": ["<writer>"]}
    ]
  }
}

    {
  "name": "support-desk",
  "type": "handoff",
  "config": {
    "workers": [
      {"kind": "agent", "agent_id": "<billing>", "matches": ["invoice", "refund"]},
      {"kind": "agent", "agent_id": "<tech>", "matches": ["error", "crash"]}
    ],
    "max_workers": 1
  }
}

    Manage workflows¶

    Action Request
    List GET .../workflows
    Get GET .../workflows/{workflow_id}
    Update PUT .../workflows/{workflow_id}; a new version is stored
    Delete DELETE .../workflows/{workflow_id}
    List versions GET .../workflows/{workflow_id}/versions
    Read a version GET .../workflows/{workflow_id}/versions/{version_number}
    Mark a version active POST .../workflows/{workflow_id}/versions/{version_number}/activate (changes the active flag only, not the config that runs; to roll back, read the version and PUT its config)
    Usage per workflow GET .../workflows/usage

    Run a workflow¶

    curl -s -X POST "$BASE/workflows/$WORKFLOW_ID/execute" \
  -H "Authorization: Bearer $ARCHY_TOKEN" -H "Content-Type: application/json" \
  -d '{"message": "Write a short note about our new refund policy"}'

    {
  "session_id": "5c9ef9bb-4dd5-4c14-b2ac-0f93f4b5f4d1",
  "output": "...",
  "structured_output": null,
  "audit": [{"agent": "writer", "...": "..."}],
  "error": null,
  "status": "completed",
  "pending_input": null
}

    The response has the final output and an audit trail of the steps. Streaming and asynchronous runs are covered in Running and streaming.

    Useful request options (all optional except message):

    Field Purpose
    session_id Continue a session, or resume a run paused at a checkpoint
    inputs Values for the inputs a composite workflow declares
    structured_output_schema JSON Schema; the final result is validated and returned as structured_output
    knowledge_base_id_override Use another knowledge base for this run
    mcp_enabled, mcp_tool_allowlist Turn MCP tools off or restrict them for this run only
    instructions_overlay Extra per-turn context for interactive orchestrators

    Convert a legacy workflow to a graph¶

    POST .../workflows/{workflow_id}/convert-to-composite returns {type, config, acknowledged_losses} for the equivalent composite graph without saving it. Types with no conversion return 400. If the conversion would drop settings or merge a repeated agent it fails with CONVERSION_LOSSES and lists them; call it again with {"acknowledge_losses": true} once you accept them. Validate the result and save it with PUT using "type": "composite" and the returned config. See Composite workflow graphs.

    Choosing a type¶

    flowchart TD
    Q{What do you need?}
    Q -->|A fixed pipeline| S[sequential]
    Q -->|Independent opinions at once| P[parallel]
    Q -->|Pick the right specialist| R[routing or handoff]
    Q -->|Stages with fan-out and fan-in| ST[staged]
    Q -->|A manager and workers| O[orchestrator]
    Q -->|Challenge and decide| D[debate]
    Q -->|Conditions, loops, human approval, files| C[composite]
