    Composite workflow graphs¶

    A composite workflow is a graph: typed nodes joined by typed edges, plus declared inputs and variables. It can branch on conditions, loop, run branches in parallel, merge results, pause for a human, call other workflows and save files.

    This page teaches by building graphs. The authoritative, always current contracts are served by the API (and as MCP tools), so read them when you generate graphs programmatically:

    Contract REST MCP tool
    Authoring guide (Markdown) GET /api/v1/workflow-authoring-guide workflow_authoring_guide_get
    Node type registry GET /api/v1/workflow-node-types workflow_node_types_get
    JSON Schema of the definition GET /api/v1/workflow-definition-schema workflow_definition_schema_get
    Validation and run error codes GET /api/v1/workflow-validation-codes workflow_validation_codes_get

    The definition¶

    A composite workflow has type: "composite" and a config that is a version 2 definition:

    {
  "version": 2,
  "inputs": [],
  "variables": {},
  "graph": {"nodes": [], "edges": []}
}
    • Node: {id, type, data, position}. id is unique. data.name is the reference name other nodes use as nodes.<name> (lowercase letters, digits and underscores, starting with a letter, at most 48 characters). position is {x, y} and only matters for editors.
    • Edge: {id, source, target, sourceHandle?, targetHandle?, data?}. The connection type is read from data.connectionType, default sequential.
    • Exactly one start node and at least one end node. A path must lead from start to an end and no node may be left unconnected (ORPHAN_NODE); a node that start cannot reach is a warning (UNREACHABLE_NODE). A cycle is allowed only through a loop node.
    • Unknown keys are preserved, so editors can store their own fields.

    Your first graph¶

    Two agents in a row, with a declared input:

    {
  "name": "research-and-write",
  "type": "composite",
  "config": {
    "version": 2,
    "inputs": [{"name": "topic", "type": "string", "required": true}],
    "graph": {
      "nodes": [
        {"id": "start", "type": "start", "data": {}},
        {"id": "a1", "type": "agent", "data": {"name": "researcher", "agentId": "<agent id>", "prompt": "Research: {{input.topic}}"}},
        {"id": "a2", "type": "agent", "data": {"name": "writer", "agentId": "<agent id>", "prompt": "Write a summary of:\n{{nodes.researcher.output}}"}},
        {"id": "end", "type": "end", "data": {}}
      ],
      "edges": [
        {"id": "e1", "source": "start", "target": "a1"},
        {"id": "e2", "source": "a1", "target": "a2"},
        {"id": "e3", "source": "a2", "target": "end"}
      ]
    }
  }
}

    flowchart LR
    S((start)) --> R[agent: researcher]
    R --> W[agent: writer]
    W --> E((end))

    Create it with POST .../workflows, then run it:

    curl -s -X POST "$BASE/workflows/$WORKFLOW_ID/execute" \
  -H "Authorization: Bearer $ARCHY_TOKEN" -H "Content-Type: application/json" \
  -d '{"message": "Research request", "inputs": {"topic": "vector databases"}}'

    Node types¶

    Type Category Purpose Key data fields
    start terminal Entry point none
    end terminal Exit point none
    agent agent Runs a configured agent agentId (required), name, prompt, role, outputSchema, required_mcp_servers
    hub agent Coordinates agents as a hub. Passes its input through at run time. agentId (required), name, prompt
    msghub agent Multi-agent conversation on a shared hub name, maxRounds, announcement
    pipeline flow Runs several agents sequentially or fanned out agentIds (required), mode (sequential or fanout), prompt, outputSchema
    router flow Declares labelled route branches. Passes its input through at run time: all outgoing edges run. Use condition to choose one. agentId (required), name, prompt
    condition flow Branches on a field comparison field, operator (equals, not_equals, contains, greater_than), value
    loop flow Repeats a body until a condition holds or the limit is reached conditionField (required), conditionValue, maxIterations (required)
    merge flow Combines parallel branches strategy (concatenate, summarize, pick_best), instruction, outputSchema
    checkpoint flow Pauses for human input prompt, timeoutSeconds
    sub-workflow flow Runs another workflow as a step workflowId (required)
    save-file sink Saves output as a file (artifact) source, format, fileName, overwrite
    storage-read, storage-write, storage-list integration Read, write and list files in a storage connection connectionId, location, parent, ...
    satellite-mcp, satellite-kb, satellite-skill resource Attach an MCP server, knowledge base or skill to an agent or pipeline satelliteType, resourceId, toolAllowlist

    GET /api/v1/workflow-node-types returns the full registry: required fields, ports (handles) and which node types each node may connect to.

    Connection types¶

    data.connectionType Meaning
    sequential (default) Run the target after the source
    consult An agent consults another agent
    handoff An agent hands the conversation over
    route A labelled branch out of a condition (or router); needs a label in data.condition
    attachment A resource node attached to an agent or pipeline; carries no data and schedules nothing

    Patterns¶

    Route to a specialist¶

    router and hub nodes pass their input through

    At run time a router (and a hub) node does not call its agent or choose a branch: every outgoing edge runs. To send a request to one of two specialists, classify it with an agent that returns structured output and branch with a condition node (Branch on a value). For more than two branches chain condition nodes, or use the legacy routing workflow type.

    Parallel branches and merge¶

    Two edges leave start; a merge node combines the results. A merge needs at least two incoming branches.

    {
  "nodes": [
    {"id": "s", "type": "start", "data": {}},
    {"id": "a", "type": "agent", "data": {"name": "pricing", "agentId": "<agent>"}},
    {"id": "b", "type": "agent", "data": {"name": "legal", "agentId": "<agent>"}},
    {"id": "m", "type": "merge", "data": {"name": "combined", "strategy": "summarize"}},
    {"id": "e", "type": "end", "data": {}}
  ],
  "edges": [
    {"id": "e1", "source": "s", "target": "a"},
    {"id": "e2", "source": "s", "target": "b"},
    {"id": "e3", "source": "a", "target": "m", "targetHandle": "target-top-1"},
    {"id": "e4", "source": "b", "target": "m", "targetHandle": "target-top-2"},
    {"id": "e5", "source": "m", "target": "e"}
  ]
}

    Strategies: concatenate joins the outputs, summarize asks a model to summarize them, pick_best chooses one. maxConcurrency (1 to 32, default 8) at the top of the definition limits how many agent and sub-workflow calls run at the same time.

    Branch on a value¶

    Use structured output so the condition has a field to read.

    {
  "nodes": [
    {"id": "s", "type": "start", "data": {}},
    {"id": "a", "type": "agent", "data": {
      "name": "classify", "agentId": "<agent>",
      "outputSchema": {"type": "object", "properties": {"urgent": {"type": "boolean"}}, "required": ["urgent"]}
    }},
    {"id": "c", "type": "condition", "data": {"name": "gate", "field": "urgent", "operator": "equals", "value": "true"}},
    {"id": "x", "type": "agent", "data": {"name": "escalate", "agentId": "<agent>"}},
    {"id": "y", "type": "agent", "data": {"name": "normal", "agentId": "<agent>"}},
    {"id": "e", "type": "end", "data": {}}
  ],
  "edges": [
    {"id": "e1", "source": "s", "target": "a"},
    {"id": "e2", "source": "a", "target": "c"},
    {"id": "e3", "source": "c", "target": "x", "sourceHandle": "source-true", "data": {"connectionType": "route", "condition": "yes"}},
    {"id": "e4", "source": "c", "target": "y", "sourceHandle": "source-false", "data": {"connectionType": "route", "condition": "no"}},
    {"id": "e5", "source": "x", "target": "e"},
    {"id": "e6", "source": "y", "target": "e"}
  ]
}

    A condition needs at least two route edges with distinct labels. How it works at run time:

    • field is a key of the incoming JSON object, which is the output of the upstream node (use outputSchema so the agent returns JSON). It is not a template: {{nodes.classify.json.urgent}} would be rendered first and its result used as the key, which never matches. Leave field empty to compare the whole input text.
    • operator is equals, not_equals, contains or greater_than. Comparisons ignore case; greater_than compares numbers.
    • When the condition holds, edges labelled true or yes run; otherwise edges labelled false or no run. An edge labelled default (or with no label) always runs. Any other label is accepted by validation but never taken. The label is data.condition, or true/false from sourceHandle source-true/source-false when no label is set.

    Loop until done¶

    {
  "nodes": [
    {"id": "s", "type": "start", "data": {}},
    {"id": "l", "type": "loop", "data": {"name": "refine", "conditionField": "done", "conditionValue": "true", "maxIterations": 3}},
    {"id": "w", "type": "agent", "data": {"name": "rewrite", "agentId": "<agent>"}},
    {"id": "v", "type": "agent", "data": {"name": "review", "agentId": "<agent>", "outputSchema": {"type": "object", "properties": {"done": {"type": "boolean"}}}}},
    {"id": "e", "type": "end", "data": {}}
  ],
  "edges": [
    {"id": "e1", "source": "s", "target": "l"},
    {"id": "e2", "source": "l", "target": "w", "sourceHandle": "source-body"},
    {"id": "e3", "source": "w", "target": "v"},
    {"id": "e4", "source": "v", "target": "l"},
    {"id": "e5", "source": "l", "target": "e", "sourceHandle": "source-exit"}
  ]
}

    The body leaves from source-body and comes back to the loop node; the continuation leaves from source-exit. conditionField is a key of the JSON output of the node that returns to the loop (here the review agent's structured output), not a template. The loop exits when that value equals conditionValue (ignoring case). maxIterations must be above 0; it is clamped to 1 to 50 and defaults to 5.

    Pause for approval¶

    {
  "nodes": [
    {"id": "s", "type": "start", "data": {}},
    {"id": "a", "type": "agent", "data": {"name": "draft", "agentId": "<agent>"}},
    {"id": "k", "type": "checkpoint", "data": {"name": "approval", "prompt": "Approve this draft?\n{{nodes.draft.output}}"}},
    {"id": "b", "type": "agent", "data": {"name": "publish", "agentId": "<agent>", "prompt": "Finalize: {{nodes.draft.output}}\nReviewer said: {{nodes.approval.output}}"}},
    {"id": "e", "type": "end", "data": {}}
  ],
  "edges": [
    {"id": "e1", "source": "s", "target": "a"},
    {"id": "e2", "source": "a", "target": "k"},
    {"id": "e3", "source": "k", "target": "b"},
    {"id": "e4", "source": "b", "target": "e"}
  ]
}

    The run stops with status: "awaiting_input" and the rendered prompt. The answer becomes the checkpoint node's output, here {{nodes.approval.output}}. See Human approval checkpoint.

    Attach resources¶

    Give an agent a knowledge base, MCP server or skill by adding a resource node and an attachment edge from the resource to the agent:

    {
  "nodes": [
    {"id": "s", "type": "start", "data": {}},
    {"id": "a", "type": "agent", "data": {"name": "support", "agentId": "<agent>"}},
    {"id": "kb", "type": "satellite-kb", "data": {"satelliteType": "kb", "resourceId": "<knowledge base id>"}},
    {"id": "e", "type": "end", "data": {}}
  ],
  "edges": [
    {"id": "e1", "source": "s", "target": "a"},
    {"id": "e2", "source": "a", "target": "e"},
    {"id": "e3", "source": "kb", "target": "a", "data": {"connectionType": "attachment"}}
  ]
}
    • resourceId is the id of the knowledge base, MCP server or skill. satelliteType is kb, mcp or skill and must match the node type.
    • For MCP you can add toolAllowlist (at most 100 unique tool names) to expose only some tools.
    • Limits per target: 5 MCP servers and 3 knowledge bases. One resource node may serve several agents. Routers, hubs and message hubs take no attachments.

    Save a file¶

    {"id": "f", "type": "save-file", "data": {"name": "save", "format": "markdown", "fileName": "report", "source": "workflow_output"}}

    Formats: markdown, text, json, html, csv, docx, xlsx. The node outputs the file as an artifact, also readable as nodes.save.files.

    Inputs, variables and expressions¶

    Text fields of a node (for example prompt) accept {{ expression }}.

    Source Reads
    input.<name> A declared run input. input.message is the run message.
    vars.<name> A value from variables
    nodes.<name>.output The text output of an earlier node
    nodes.<name>.json.<path> A field of a structured output, for example nodes.classify.json.items[0].id
    nodes.<name>.files Files an earlier node produced
    run, now, loop, item Run metadata, time, loop and item context

    Filters chain with |: date, default, eq, first, gt, gte, if, join, json, last, length, lower, lt, lte, ne, not, number, replace, split, trim, truncate, upper, url_encode. Example: {{ input.topic | trim | upper }}.

    Rules:

    • Reference only nodes that run before the node holding the expression, and only names that exist.
    • nodes.<name>.json.<path> must lie inside that node's outputSchema when it has one.
    • Declare inputs as {name, type, required, default, description, sensitive} with type string, number, boolean or json. message is reserved.
    • A sensitive input is masked as *** in stored traces. Do not use it in checkpoint prompts or file names.
    • Invalid inputs at run time return 422 with detail.code = WORKFLOW_INPUTS_INVALID and a list of {name, code, message}.

    Structured output¶

    Set data.outputSchema (a JSON Schema subset) on an agent, pipeline or merge node to get validated JSON, readable as nodes.<name>.json.<path>. A result that does not match fails the node with SCHEMA_VALIDATION_FAILED after the repair attempts, and a node error fails the run. On a merge node the schema applies only to the summarize and pick_best strategies (with concatenate it is ignored and validation warns OUTPUT_SCHEMA_IGNORED).

    Validate before you save¶

    POST .../workflows/{workflow_id}/validate checks a graph and returns every issue. Send an unsaved graph in the body, or an empty object to check the saved one. Add "requireNames": true to get NODE_NAME_MISSING warnings.

    curl -s -X POST "$BASE/workflows/$WORKFLOW_ID/validate" \
  -H "Authorization: Bearer $ARCHY_TOKEN" -H "Content-Type: application/json" \
  -d '{"graph": {"nodes": [], "edges": []}}'

    {
  "valid": false,
  "errors": [
    {"code": "NO_START", "message": "Workflow must have exactly one start node", "severity": "error", "node_id": null, "edge_id": null, "input_name": null, "field": null},
    {"code": "NO_END", "message": "Workflow must have at least one end node", "severity": "error", "node_id": null, "edge_id": null, "input_name": null, "field": null}
  ],
  "warnings": [
    {"code": "EMPTY_WORKFLOW", "message": "Workflow has no executable nodes", "severity": "warning", "node_id": null, "edge_id": null, "input_name": null, "field": null}
  ]
}

    Errors must be fixed before you run the workflow; warnings are advice. Saving rejects (422) invalid, reserved or duplicate node names, errors in the inputs declaration, invalid outputSchema values, invalid required_mcp_servers and attachment errors, and an unsupported or invalid definition. Graph-shape errors (start and end nodes, reachability, branches, agent references, template references) are not rejected at save time and surface when the run starts (for example 400 Composite workflow must have a Start node), so always validate first. Common codes:

    Code Meaning and fix
    NO_START, MULTIPLE_START, NO_END Exactly one start and at least one end
    START_UNREACHABLE_END Connect the graph so an end node is reachable
    ORPHAN_NODE (error), UNREACHABLE_NODE (warning) Connect the node or remove it
    CYCLE_OUTSIDE_LOOP Cycles are allowed only through a loop node
    NODE_NAME_INVALID, NODE_NAME_DUPLICATE, NODE_NAME_RESERVED Use a unique lowercase name that is not input, item, loop, nodes, now, run or vars
    AGENT_REF_MISSING An agent, router or hub node needs an agentId of an agent in this project
    CONDITION_BRANCHES, ROUTER_ROUTES Add route edges with distinct, non-empty labels
    MERGE_INPUTS A merge needs two or more incoming branches
    LOOP_BODY Set conditionField and maxIterations above 0
    SCHEMA_INVALID outputSchema uses features outside the supported subset
    TEMPLATE_NODE_NOT_UPSTREAM A template reads nodes.<name> of a node that does not run before it. Reorder the graph or read an earlier node.
    MCP_UNAVAILABLE (run) A required MCP server was not connected

    The complete catalog with meanings, severities and fix hints is GET /api/v1/workflow-validation-codes.

    Workflow for generating graphs

    1. Read the node type registry and the definition schema.
    2. Draft the graph with one start and one end.
    3. Call validate with the draft in the body; fix every error; repeat until valid is true. Validation needs an existing workflow id in the path, so create a placeholder workflow first (for example with an empty graph) and update it when the draft is valid.
    4. Save with POST (new) or PUT (existing), then validate the saved workflow once more with an empty body.
    5. Run a test execution and inspect the trace.

    Run behaviour to know¶

    • A node error fails the run. No later node starts and there are no error edges. The run status is failed, error is set and output is empty.
    • An agent node only sees the output of its incoming edges. To pass the run message plus the previous result plus an instruction, set the target's data.prompt, for example {{input.message}} then Previous result: {{nodes.<previous>.output}}. The prompt replaces the node input.
    • An edge data.instructions (legacy alias instruction) is rendered and appended to that edge's output for agent, sub-workflow, message hub and pipeline targets. A target's own non-empty prompt replaces the input, including the instruction.
    • Top-level required_mcp_servers applies to every agent node (including agents a hub fans out to, but not agents inside router or pipeline nodes); data.required_mcp_servers adds servers for one node. If a required server is not connected the node fails with MCP_UNAVAILABLE. Without the list, an unreachable server is skipped.

    Storage nodes¶

    storage-read, storage-write and storage-list use a storage connection (Google Drive, OneDrive or Dropbox) of the project.

    • data.connectionId is a literal UUID, never a template.
    • storage-read copies a file into an artifact and passes its input through. storage-write writes text or an earlier file into a folder and takes conflict of fail (default), overwrite or new_version. storage-list returns {entries, nextCursor}.
    • Errors carry stable codes such as storage_not_found, storage_permission_denied, storage_file_too_large and storage_path_not_allowed, and never a file path.
    • A connection without a root folder allows no write. For Google Drive the scope is drive.file: a node sees only files the app created or the user picked.

    Versions¶

    Every PUT that leaves the workflow with a config stores a version snapshot (creating does not).

    curl -s "$BASE/workflows/$WORKFLOW_ID/versions" -H "Authorization: Bearer $ARCHY_TOKEN"
curl -s "$BASE/workflows/$WORKFLOW_ID/versions/2" -H "Authorization: Bearer $ARCHY_TOKEN"

    POST .../versions/{n}/activate only changes which version is flagged active; it does not change the config that runs. To roll back, read the old version and PUT its config back.

    Python: create, validate, run¶

    import httpx


def deploy_graph(client: httpx.Client, scope: str, name: str, config: dict) -> str:
    """Create the workflow, then refuse to use it when validation reports errors."""
    created = client.post(f"{scope}/workflows", json={"name": name, "type": "composite", "config": config})
    created.raise_for_status()
    workflow_id = created.json()["id"]

    report = client.post(f"{scope}/workflows/{workflow_id}/validate", json={}).json()
    if not report["valid"]:
        client.delete(f"{scope}/workflows/{workflow_id}")
        raise ValueError([f"{e['code']}: {e['message']}" for e in report["errors"]])
    return workflow_id


def run(client: httpx.Client, scope: str, workflow_id: str, message: str, **inputs) -> dict:
    r = client.post(
        f"{scope}/workflows/{workflow_id}/execute",
        json={"message": message, "inputs": inputs or None},
        timeout=300,
    )
    r.raise_for_status()
    return r.json()
